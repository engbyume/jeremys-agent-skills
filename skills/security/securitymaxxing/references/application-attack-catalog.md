## How to use this catalog

This non-exhaustive catalog supports threat modeling for apps, websites, APIs, and games. An entry is a possible attack path, not proof that a product has that vulnerability. Select risks that match the architecture and threat model, then map them to the existing 70 core and 23 conditional checks. This is an example catalog, not a second mandatory checklist.

The submitted list contains 21 numbered scenarios, although its introduction says 20. Items 14 and 16 both describe padding-oracle attacks. Both labels remain for traceability, but they count as one attack family. Items 22-101 are 80 additional scenarios. Each entry gives a preventive control and a first response.

This is defensive guidance. Do not run attack simulations against a live or third-party target without current authorization and a defined scope. Do not retaliate against an attacker by probing or attacking their systems.

## User-provided scenarios 1-21

| # | Scenario | Prevent | Detect and respond |
|---|---|---|---|
| 1 | HTTP/2 Rapid Reset can exhaust server resources. | Patch the HTTP/2 server and edge proxy. Apply provider mitigations, stream and connection limits, and rate controls. | Alert on unusual reset-to-request ratios, stream churn, and saturation. Apply edge mitigation, scale or fail over, then verify every HTTP/2 termination point is patched. |
| 2 | An overlong username, including one 52 characters long, triggers inconsistent parsing. | Fifty-two characters is not a universal vulnerability. Set one documented limit in bytes and characters, validate before persistence, and reject instead of silently truncating. | Alert on parser or database length errors. Align limits across login, signup, federation, API, and storage paths. |
| 3 | A forged SAML response or assertion creates a false login. | Use a maintained SAML library. Verify the exact signed assertion consumed, trusted issuer and key, audience, recipient, destination, time bounds, request correlation, and one-time assertion ID. | Reject any signature or claim mismatch. If a signing key may be compromised, disable it, revoke affected sessions, and review sign-in records. |
| 4 | A spoofed Microsoft email claim links or authorizes the wrong account. | Validate the token signature, issuer, audience, expiry, nonce, and allowed tenant. Key accounts by stable subject identifiers such as tenant plus object ID, not email or display-name claims. | Deny mismatches. Unlink suspicious accounts, revoke sessions, and review account-linking history. |
| 5 | GraphQL aliases or batches brute-force a 2FA code while appearing as one request. | Enforce attempt limits inside the authentication resolver per account and challenge. Bound aliases, operations, batch size, and query cost. Do not batch sensitive authentication mutations. | Detect many OTP attempts inside one request. Throttle or stop the challenge, require fresh proof, and avoid account-wide lockout that enables denial of service. |
| 6 | A valid 2FA code is replayed. | Atomically mark accepted one-time codes or TOTP time steps as used. Keep validity windows narrow and rate-limit attempts. | Reject reused codes and record the event. If the factor may be compromised, revoke it and require re-enrollment. |
| 7 | A regular expression freezes a request worker through catastrophic backtracking. | Prefer linear-time regex engines or patterns without nested ambiguous repetition. Bound input length and execution time. | Alert on regex latency and worker CPU. Disable the affected path, patch the pattern or engine, and keep the input limit. |
| 8 | A JWT verifier accepts a token signed with a public key as though that key were a secret. | Pin the expected algorithm and key type for each issuer. Use a maintained verifier, trusted key sources, and strict issuer, audience, expiry, and claim checks. | Reject unexpected algorithm or key metadata. If a signing key was mishandled, rotate it and invalidate tokens signed under the affected configuration. |
| 9 | HTTP request smuggling sends a hidden request past a proxy. | Patch and configure the proxy and origin to parse message framing consistently. Reject ambiguous framing and close the connection after malformed requests. | Alert on parser disagreement, unexpected downstream requests, or desynchronization. Disable reuse of affected connections, patch every hop, and inspect cache and origin logs. |
| 10 | An attacker poisons a shared cache through a header that the cache key ignores. | Cache only on normalized, allowlisted inputs that change the response. Strip untrusted forwarding headers and bypass shared caching for personalized responses. | Find unexpected cache variants and mismatched cache keys. Purge affected entries and disable caching for the route until corrected. |
| 11 | An attacker spoofs a forwarded client IP to bypass rate limits. | Trust forwarding headers only from configured proxy hops. Strip client-supplied forwarding values at the edge and combine trusted IP, account, session, and operation limits. | Alert on inconsistent proxy chains or sudden rate-limit bypasses. Correct the trust boundary and block abusive traffic at the edge. |
| 12 | A PostgreSQL view exposes rows that base-table RLS should hide. | On supported versions, use security-invoker views when the view must honor caller policies. Check view grants, base-table policies, and the application's non-owner role separately. | Test direct and view access as each application role. Revoke unsafe grants, correct the view or policy, and assess prior reads. |
| 13 | A token generated with Math.random is predictable. | Generate security tokens with a cryptographically secure random source and sufficient entropy. Keep tokens scoped, short-lived, and single-use where appropriate. | Revoke outstanding tokens if predictable generation was used. Review token use and require fresh authentication. |
| 14 | A padding oracle leaks information through distinguishable decryption timing or errors. | Prefer authenticated encryption. Do not expose padding or decryption distinctions; use vetted constant-time cryptographic libraries and verify authentication before using plaintext. | Remove the oracle path, rotate affected keys, invalidate derived tokens or ciphertext, and review access logs. |
| 15 | Secret comparison timing helps guess a token. | Use a vetted constant-time comparison for fixed-length secrets. Keep surrounding validation and error behavior from leaking secret-dependent timing. | Replace unsafe comparisons, rotate exposed tokens, and review repeated near-match attempts. |
| 16 | A padding oracle is reported again as a separate attack. | Treat this as the same attack family as item 14 unless the concrete system reveals a different oracle. Apply authenticated encryption and uniform failure handling. | Deduplicate the finding, preserve both report references, and track remediation under one padding-oracle issue. |
| 17 | Prototype pollution changes object behavior and may reach a code-execution gadget. | Reject dangerous property names at untrusted object boundaries. Use safe parsing and merge APIs, avoid dynamic code sinks, and keep affected runtimes and libraries current. | Alert on unexpected prototype changes or child processes. Disable the vulnerable path, patch, restart affected workers, and review actions taken with polluted objects. |
| 18 | User-controlled template source executes on the server. | Treat templates as trusted code and user content as data. Do not compile untrusted templates; restrict template capabilities and apply context-appropriate escaping. | Disable the affected renderer, preserve samples and logs, remove malicious templates, and rotate secrets the renderer could access. |
| 19 | An XML parser resolves external entities and reads files or makes network requests. | Disable DTDs, external entities, XInclude, and unapproved external schemas for untrusted XML. Use a maintained parser and resource limits. | Alert on unexpected file or outbound network access. Disable the parser path, inspect affected inputs, and review host and egress logs. |
| 20 | A browser is tricked into opening an authenticated WebSocket from an attacker-controlled site. | Validate the handshake Origin against an exact allowlist. Authenticate connections, authorize each channel and message, and expire or reauthorize stale sessions. | Monitor unexpected origins, session use, and message patterns. Close connections, revoke sessions, and review exposed channels. |
| 21 | A Unicode-confusable username impersonates another account. | Normalize identifiers consistently and check security-sensitive names for confusable collisions using a current Unicode profile. Warn or reserve collisions without banning legitimate scripts across all text. | Review reports and impersonation evidence. Reserve or rename deceptive identifiers and notify affected users. |

## Additional identity and API scenarios 22-61

The source anchors for these scenarios include NIST SP 800-63B-4, RFC 9700, Microsoft identity claim guidance, and the OWASP API Security Top 10. These scenarios expand examples already covered by the general checklist.

| # | Scenario | Prevent | Detect and respond |
|---|---|---|---|
| 22 | Credential stuffing reuses passwords leaked from other services. | Use MFA or risk-based step-up, breached-password screening, and account-aware throttling. | Detect distributed login failures or valid-password/MFA-failure patterns. Challenge, revoke affected sessions, and notify users. |
| 23 | Password spraying tries a common password against many accounts at a low rate. | Combine per-account throttling with signals across accounts, devices, and networks. | Detect one source or device touching many accounts. Challenge or block it and review affected accounts. |
| 24 | Account enumeration reveals which email addresses or usernames are registered. | Use consistent responses, status codes, and timing for login, signup, recovery, and invitations. | Detect broad account probes, throttle them, and review related authentication activity. |
| 25 | Common or already-compromised passwords are accepted. | Block common, expected, and known-compromised passwords while following current password guidance. | Track repeated blocked-password attempts. Require a change when evidence indicates an account password was exposed. |
| 26 | A stolen password database enables cheap offline cracking. | Store passwords with a vetted adaptive salted password hash, not plaintext or fast general-purpose hashes. | After a credential-store breach, force affected password changes, invalidate sessions, and review authentication activity. |
| 27 | Password-reset flooding overwhelms a user's email or phone. | Rate-limit reset requests per account and apply bot controls without revealing account existence. | Detect delivery bursts, slow or suppress further requests, and notify the account owner through an established channel. |
| 28 | A reset token leaks through referrers, third-party resources, browser history, or logs. | Use short-lived single-use tokens, HTTPS, a no-referrer policy, no third-party resources on reset pages, and log redaction. | Revoke outstanding reset tokens if exposure is suspected. Remove exposed values from logs where possible and review access. |
| 29 | A reset link uses an attacker-controlled Host or forwarded-host value. | Build links from a fixed or explicitly allowlisted public origin. Trust forwarded-host values only from known proxies. | Alert on unexpected host values. Revoke links generated from them and correct the proxy or origin configuration. |
| 30 | Guessable knowledge questions are the only account-recovery proof. | Do not use personal knowledge questions as the sole recovery method. Use recovery evidence appropriate to the account's risk. | Review repeated recovery attempts and require verified recovery proof before restoring access. |
| 31 | A newly changed recovery address or number is immediately used to take over an account. | Require independent previously established evidence and notify existing verified channels before high-risk recovery. | Flag recovery soon after contact changes. Suspend recovery for review and restore only after verified ownership checks. |
| 32 | A fallback login path silently accepts weaker authentication than the primary path. | Keep fallback assurance appropriate to the account and use a controlled recovery process. | Alert on fallback use by MFA-enrolled accounts. Review the login and invalidate suspicious sessions. |
| 33 | A SIM swap or number port redirects SMS authentication codes. | Offer stronger alternative authenticators and treat carrier-change signals as risk indicators before relying on SMS. | Pause SMS authentication when transfer signals appear and require another factor. Review sessions started near the transfer. |
| 34 | Repeated MFA push prompts lead a user to approve an attempt they did not start. | Limit prompt frequency and require explicit transaction context or an authenticator secret instead of approval-only prompts. | Detect repeated prompts or unusual approvals. Suspend the factor, revoke sessions, and notify the user. |
| 35 | A compromised session binds an attacker-controlled authenticator or replaces the user's factor. | Require an existing factor or fresh reauthentication for factor changes. Notify an independent channel and treat changes as high risk. | Alert on new factor bindings. Revoke unauthorized bindings and sessions, then review recovery activity. |
| 36 | A lost or reported-compromised authenticator remains valid. | Provide prompt suspension or invalidation and prevent it from being rebound without verified recovery. | Alert on use after a loss report. Revoke it and review sessions created with that factor. |
| 37 | A session ID known before login remains valid after authentication. | Accept only server-created session IDs and rotate them after login and privilege changes. | Detect unissued or reused IDs. Terminate the session and review related activity. |
| 38 | A stolen session remains active because expiry is only checked in the client. | Enforce idle and absolute session timeouts on the server. | Alert on sessions beyond policy. Invalidate them and require reauthentication. |
| 39 | Logout removes the cookie but leaves the server-side session valid. | Revoke server-side sessions and all identifiers in their rotation chain on logout. | Detect use of terminated sessions. Revoke the chain and investigate the account. |
| 40 | Password reset leaves older sessions active for an attacker. | Invalidate existing sessions during recovery or password changes unless the product has a justified, secure exception. | Detect old-session use after reset. Revoke those sessions and notify the account owner. |
| 41 | A weak or broad session cookie exposes authentication across channels or subdomains. | Set Secure, HttpOnly, and suitable SameSite attributes. Prefer narrow host-only scope and short lifetimes. | Review cookie configuration and cross-origin use. Revoke sessions if exposure is suspected. |
| 42 | Loose OAuth redirect matching sends a login response to an unintended destination. | Require exact registered redirect URI matching and remove open redirects from the authentication flow. | Alert on rejected or unexpected redirect targets. Revoke affected grants or tokens if a response may have leaked. |
| 43 | OAuth state is missing, reusable, or not bound to the initiating browser session. | Use a one-time transaction state bound to the user agent, or a correctly bound PKCE design. | Detect missing, mismatched, or reused callbacks. Stop the flow and review related grants. |
| 44 | PKCE is absent or can be downgraded. | Require PKCE for public clients and reject a verifier when no challenge was present in the authorization request. | Monitor verifier mismatches and downgrade attempts. Terminate the transaction. |
| 45 | An ID token from another login transaction is accepted because nonce is missing or reused. | Bind a unique nonce to the user-agent session and validate it before using tokens. | Detect mismatches or reuse. Reject the login and review related token activity. |
| 46 | A client interacting with multiple authorization servers sends a code or token to the wrong server. | Bind each transaction to its expected issuer and endpoints, then verify that binding on callback. | Flag issuer or endpoint mismatches. Stop the flow and revoke exposed credentials. |
| 47 | An authorization code is injected from another transaction or redeemed more than once. | Bind codes to the client, redirect URI, and transaction with PKCE. Make codes single-use and short-lived. | Detect duplicate redemption or binding mismatches. Revoke tokens issued from the affected code. |
| 48 | An implicit flow or token-bearing URL exposes access tokens through history, referrers, or logs. | Use the authorization-code flow and do not place access tokens in URI query parameters. | Search for token-bearing requests or logs. Revoke affected tokens and remove exposed values. |
| 49 | A stolen refresh token is replayed to mint new access tokens. | Rotate or sender-constrain refresh tokens where supported. Bind them to approved scopes and resources. | Alert on reuse of an invalidated token. Revoke the token family and require fresh authorization. |
| 50 | A token for one service or action is accepted by another service. | Restrict token audience and scope to the intended resource and action. Enforce them at every resource server. | Reject cross-resource or out-of-scope use. Revoke the token if misuse is suspected. |
| 51 | A browser or mobile app relies on an embedded OAuth client secret. | Register public clients as public. Do not rely on a shipped value as proof that a client is confidential. | If a shipped secret is exposed, rotate it where applicable and review its use. |
| 52 | The same federated subject ID is treated as globally unique across identity providers. | Key federated identities by issuer and subject together. Validate the expected issuer for each transaction. | Detect ambiguous account links and quarantine them for verified resolution. |
| 53 | An authenticated user accesses another user's object through an API identifier. | Authorize every object and action on every request, including nested and batch operations. | Alert on cross-owner denials or unexpected successes. Audit affected records and contain exposure. |
| 54 | A regular user reaches an administrative API function. | Deny by default and grant each function explicitly by role or policy. | Alert on privileged calls from non-privileged identities. Revoke access and review resulting changes. |
| 55 | An API returns sensitive object fields or lets a client change protected fields. | Allowlist response and writable fields. Validate schemas and return only data the caller needs. | Alert on unexpected sensitive-field reads or changes. Audit and reverse unauthorized modifications. |
| 56 | A client-supplied tenant ID is trusted without checking membership. | Derive tenant context from authenticated membership and enforce it for every operation. | Alert on cross-tenant attempts or successes. Block access and assess possible exposure. |
| 57 | Exports or pagination allow bulk extraction without the right permission or limits. | Require export permissions, cap page and export sizes, and minimize returned fields. | Alert on unusual download volume. Suspend export access and assess affected data. |
| 58 | Credentialed CORS lets an unintended origin read account data. | Allowlist exact origins and enable credentials only where required. | Review origin and access logs. Restrict the policy and assess whether sensitive responses were accessed. |
| 59 | Repeated or costly API requests exhaust compute, storage, or paid services. | Set per-user quotas and limits on request size, page size, concurrency, and processing cost. | Monitor latency, cost, and request-volume spikes. Throttle or suspend abusive clients. |
| 60 | Automation abuses a sensitive business flow such as reservations or posting. | Apply flow-specific limits and anomaly checks. Add verification where the business risk warrants it. | Detect unusual booking, purchase, or posting rates. Pause the flow for affected accounts and reconcile changes. |
| 61 | WebAuthn accepts an assertion with the wrong origin or relying-party ID. | Validate the expected origin, challenge, and RP ID on the server for every ceremony. Use only approved origins and RP ID scope. | Reject mismatches. Review failed ceremonies and revoke credentials if a relying-party configuration was exposed. |

## Additional browser, infrastructure, mobile, and game scenarios 62-101

The source anchors include OWASP browser and file-handling guidance, IETF HTTP and DNS specifications, MITRE CWE entries, GitHub and cloud-provider security documents, Android and Apple platform guidance, and official game-engine documentation.

| # | Scenario | Prevent | Detect and respond |
|---|---|---|---|
| 62 | Untrusted data reaches an unsafe browser DOM sink and becomes DOM-based XSS. | Build text with safe DOM APIs. Use Trusted Types where supported and treat CSP as a backup layer. | Monitor CSP violations, trace the affected sink, and remove or encode the offending data. |
| 63 | A browser sends an unintended state change using the user's existing site credentials. | Use CSRF tokens and verify Origin or Referer on protected requests. Set suitable SameSite cookies. | Alert on invalid tokens or origins, review affected changes, and reverse them where possible. |
| 64 | Another site frames the app and tricks a user into activating controls. | Set CSP frame-ancestors or X-Frame-Options on routes that must not be framed. | Monitor CSP reports, identify affected routes, and block framing while reviewing actions taken through them. |

| 66 | A third-party script changes and runs with the page's browser privileges. | Minimize vendor scripts, pin stable assets with SRI where possible, or isolate them in sandboxed frames. | Alert on hash or CSP changes. Disable the script and review vendor access and loaded content. |
| 67 | A service worker controls pages or responses outside its intended application area. | Keep the worker script and registration scope narrow. Review worker update and cache rules. | Track approved worker versions and scopes. On an unexpected change, serve a clean update and inspect cached responses. |
| 68 | A browser interprets an uploaded file as a more active type than the server intended. | Set accurate Content-Type headers and X-Content-Type-Options: nosniff. | 69 | An HTTPS page loads an active resource over unencrypted HTTP. | Serve resources over HTTPS, use HSTS where appropriate, and deploy CSP mixed-content protections. | Review browser reports and remove or upgrade the insecure resource. |
| 70 | A page or embedded origin receives unneeded camera, microphone, or location access. | Restrict Permissions Policy and iframe allow attributes to required features and trusted origins. | Audit policy headers and feature use. Remove grants to unexpected origins. |
| 71 | A browser reaches a local or internal service through a hostname whose address changes. | Validate Host and Origin, require authentication for local services, and bind listeners only where needed. | Alert on unexpected hosts reaching local listeners. | 72 | An abandoned DNS target, delegated zone, or subdomain is taken over. | Remove dangling records, protect registrar accounts, and require review for DNS delegation changes. | Alert on NS, DS, address-record, and certificate changes. Restore known-good records and review issuance. |

| 88 | A build installs a similarly named public package instead of the intended dependency. | Use scoped private package names, explicit registry mapping, lockfiles, and dependency review. | Alert on new package names or unexpected registries. Remove the dependency and rebuild in a clean environment. |
| 89 | A dependency install script accesses files or credentials during a build. | Review lifecycle scripts and run dependency installation in an isolated, least-privilege build environment. | Review script changes and build egress alerts. Stop the build, revoke exposed runner credentials, and rebuild on a clean runner. |
| 90 | A cloud bucket or object becomes public or writable by mistake. | Enable account-level public-access blocks and enforce storage policy checks. | Alert on policy changes and public-access findings. Restrict access, preserve logs, and assess exposure. |
| 91 | A Kubernetes workload runs with unnecessary root or host-level privileges. | Enforce restricted Pod Security, non-root execution, dropped capabilities, and read-only filesystems where feasible. | Alert on admission or runtime policy violations. Isolate the node and redeploy with corrected settings. |
| 92 | Slow or incomplete HTTP requests hold connections and workers open. | Set request-read timeouts, minimum ingress rates, body limits, and connection caps. | Alert on long-lived incomplete requests and connection saturation. Apply edge filtering and close expired requests. |
| 93 | Large or repeated media, AI, or conversion jobs exhaust compute or cloud budget. | Bound input dimensions and work per job, cap concurrency, and set workload budgets and alerts. | Alert on cost anomalies and queue growth. Drain suspicious work and temporarily disable the expensive operation if needed. |
| 94 | Clients or services retry failures without bounds and overload an unhealthy dependency. | Use capped exponential backoff with jitter, retry budgets, and circuit breakers. | Monitor retry ratios, timeouts, and queue age. Shed load and pause retries while the dependency recovers. |
| 95 | Another Android app invokes an exported component that was intended to be private. | Set android:exported to false unless external access is required. Use signature permissions and validate incoming intent data. | Log rejected external calls and malformed inputs. Patch the component boundary and review actions it performed. |
| 96 | A page loaded in an Android WebView calls native methods with the app's permissions. | Disable JavaScript interfaces for untrusted content, allowlist navigation origins, and avoid exposing sensitive native functions. | Log blocked origins and bridge calls. Remove the bridge in a release fix and clear affected WebView data. |
| 97 | A mobile app accepts cleartext traffic or a broad TLS exception. | Enforce HTTPS with Android Network Security Configuration or Apple App Transport Security. Keep exceptions narrow and temporary. | Audit release configuration and network failures. Remove the exception and ship a corrected build. |
| 98 | Sensitive app files or databases are included in mobile backups. | Define explicit backup rules, exclude sensitive data, and use platform data-protection features. | Review backup manifests and test restore artifacts. Restrict or remove exposed copies and assess the affected data. |
| 99 | A game accepts client-reported movement, score, or gameplay state as truth. | Keep gameplay decisions on the server and validate every client action against game rules and bounds. | Flag impossible state transitions, preserve match logs, and review or roll back invalid results. |

| 101 | Excessive or costly multiplayer traffic saturates network or server capacity. | Bound packet size and processing cost. Use a relay or gateway with traffic validation and per-player limits. | Monitor packet, byte, throttle, and session metrics. Route through DDoS protection or isolate the affected fleet. |


## Incident response

Do not retaliate or run unapproved tests against an attacker's systems. Follow the product's incident plan.

1. Confirm the affected service, account, tenant, and time window. Preserve relevant logs and artifacts with access controls.
2. Contain the route or identity at the edge. Use provider-native protections and avoid deleting evidence.
3. Revoke affected sessions, tokens, keys, webhooks, and service credentials. Rotate secrets only after closing the compromised access path.
4. Patch the root cause, verify the fix in a safe environment, and restore from a known-good source when needed.
5. Assess impact and notify security, privacy, legal, provider, and affected-user owners according to the applicable plan and current obligations. Do not assume one legal deadline applies everywhere.

Use [NIST SP 800-61 Rev. 3](https://csrc.nist.gov/pubs/sp/800/61/r3/final) as incident-response guidance. It does not replace product-specific incident ownership or legal advice.
